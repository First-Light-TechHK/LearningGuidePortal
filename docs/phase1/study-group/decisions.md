# Study Group decisions

PRD v0.10 section 8.1 lists the records and fields. Target production architecture (release gate, not yet implemented): Production Study Group must use the product's selected RDS PostgreSQL store, as required by `AGENTS.md` and the release runbook. Current implementation status: the code still uses the file repository in `modules/group-study/repository.ts` in every environment. It is temporary local/test compatibility only; it is not a production deployment option, and production Study Group stays disabled until the RDS repository and the remaining release-gate items exist. When implemented, that repository will enforce the same idempotency facts with database constraints and transactions — a second join does not add a member, the same client event id returns the original tutor item, and a session has one meeting row; none of those constraints exist in the file repository today.

Where `study-group-architecture.md`, `study-group-tech-selection.md`, or `study-group-ai-tutor-plan.md` left a point open, this file is the choice.

## Tutor

The tutor is the Related Course tutor, shared in the Live Session chat. It is not a private tutor per user and not a second tutor product.

Answers are grounded by fuzzy matching inside the model call itself (owner decision, 2026-10-13): the whole stored Course Knowledge text for the course — published lesson text plus every file in the course's `knowledge/<slug>/` directory, each headed by its filename — is supplied to the model as the course material, and the model searches it for whatever answers the participant's question, matching by meaning and across languages (a Chinese question can be answered by English course material). No server-side retrieval, hit threshold, or pre-filtering exists. This is a recorded owner deviation from PRD BR-030, which requires unconditional grounding: the tutor never refuses, and every question gets a direct answer. When the material covers the question, the reply starts with a first token COURSE and is published with mode `course`. When it does not, the reply starts with GENERAL and is published with mode `general`: it is answered from general knowledge, the client renders the fixed "not from the course material" note for that mode, and the text itself never carries the note. The mode tags are parsed off the published text; a reply without a usable first token defaults to `general`, so nothing unverified can be presented as course content. The reply is structured (line 1 is the mode token, line 2 a one-sentence answer, then 0 to 3 lines starting with "• "), written in the language of the question, and capped at 220 English / 100 Chinese characters in the prompt with a server-side clamp of at most 4 lines and 120 CJK characters or 240 otherwise. Known limits while the material stays small: the whole-directory read has no per-file or total-size cap and no cache — a course whose knowledge directory grows large or gains binary files needs a size guard; the KS scheme in `docs/phase1/ks-context-scheme.md` designs that layer.

The model call is a direct chat completion. The default is OpenRouter through `fetchOpenRouter`, the same client the course tutor uses. An empty `STUDY_GROUP_TUTOR_URL` keeps that path. When that variable is an OpenAI-compatible chat completions URL, the Study Group tutor posts the same messages there and does not send OpenRouter-only fields. The model id is `STUDY_GROUP_TUTOR_MODEL`, then `OPENROUTER_MODEL`, then `openrouter/auto`. Further model settings live in the same place (runtime): `STUDY_GROUP_TUTOR_MAX_TOKENS` (default 700; a runaway guard, not the length control — the prompt plus the server clamp set the visible length; reasoning tokens share this budget on most providers) and `STUDY_GROUP_TUTOR_REASONING` (unset by default, keeping the shared OpenRouter layer's CoT default of reasoning off with a strip-on-400 retry; when set to none/minimal/low/medium/high it pins an explicit reasoning effort and gives up that retry). Model settings stay in one place so a later backoffice knowledge base can become their source. No agent framework is added.

The answer is published into the shared LiveKit room as one data message every current participant can read: `{ type: "tutor", id, text, mode, replyTo? }`. `mode` is `course`, `general`, or `unavailable`; a message that arrives without a mode is treated as `course`. The packet has no destination list. Screen, video, and exhibit pixels are not sent.

One question is in flight per Live Session. Later questions wait. Order is the server receipt time. The asker and the original text stay on the queue item. Enqueue writes that item and does not call the model. The delivery that starts for that session keeps going until every waiting question has been handled. A second delivery for the same session does not start a second model call. Every queue item settles with exactly one room message. If every key fails, the reply is empty after cleaning, or the reply contains a key secret, or no usable tutor key exists at all, the item publishes an unavailable message — mode `unavailable` and empty text — and the client renders its own "temporarily unavailable" copy. The removed material-absent sentence is never published.

## API keys

The Live Session tutor's LLM keys are a JSON list of `{ "id", "secret" }`. On auth failure, rate limit, or quota, the next healthy key is used. Request counts, errors, and latency stay in memory. The keys are hot (owner decision, 2026-10-20): with `STUDY_GROUP_TUTOR_KEYS_SECRET_ID` naming a Secrets Manager secret (`lg-<env>-studygroup-tutor-keys`), the server reads the list at run time, re-reads it at most once a minute, and re-reads it at once when every key it had was refused (then retries that question once with the new list). Adding, removing or rotating a key is an edit of the secret's value, live within a minute, with no redeploy; a failed or emptied read keeps the last good list. Without the secret id, the `STUDY_GROUP_TUTOR_KEYS` variable is the list, as before. There is no admin UI, no key file, and no secret in the repo, logs, or responses. An environment that never set it uses the site's `OPENROUTER_API_KEY` as a one-key pool (DEV and SIT had no pool on 2026-10-20, so every question answered "temporarily unavailable"); the shared key is never sent to a custom `STUDY_GROUP_TUTOR_URL` outside OpenRouter. `/api/health/config` reports which pool is in use as `studyGroup.tutorKeySource` (`secret`, `own`, `shared` or `none`). Every Secrets Manager read is cut off after 3 seconds; a read that failed before any good list is not retried for a minute, and the health surface waits at most a second for it.

## LiveKit keys and project list

Every LiveKit key and setting is hot (owner decision, 2026-10-20: adding, changing or rotating takes effect without a redeploy). Each project's key pair is read from its Secrets Manager secret at run time, kept for at most one minute, re-read at once when the provider refuses it, and kept at its last good value when a read fails. The project list is the same JSON as `LIVEKIT_PROJECTS_JSON`, kept in a Secrets Manager secret named by `LIVEKIT_PROJECTS_SECRET_ID` and read the same way (`createHotLiveKitProjectRegistry`); the JSON variable is the fallback only when that id is unset. A project that leaves the list stays resolvable as `draining` for the running process, so no live room is orphaned; new rooms go to listed `active` projects only. The one-time App Runner setting is the plain variable `LIVEKIT_PROJECTS_SECRET_ID` plus `secretsmanager:GetSecretValue` on that secret for the instance role. `STUDY_GROUP_TOKEN_LOG_KEY` is an internal log-encryption key, not a provider key, and stays injected at instance start.

## Labels and seats

The Join control for a Study Group reads "Join Now" ("立即加入" in zh-CN, per the design source). The Hosting chip is shown only when the current user is the Host. The maximum of 6 includes the Host. During Starting Soon the last seat is kept for the Host while the Host is not in (owner decision, 2026-10-19): members fill at most maximum − 1 seats, so members waiting can never lock the Host out of their own session. Once the session is live, a full session refuses another entry, including the Host, and the Host cannot start a session whose waiting members already fill every seat. The Host does not enter the member waiting flow: during Starting Soon the Host's control is Start Live Session, and a Host visible on the waiting screen is told to start when ready instead of reading the member wording.

## Seats and the end of a Live Session

The server is the only source of truth for who holds a seat (owner decision, 2026-10-19; `modules/group-study/presence.ts`). A seat is a lease: entering grants it, the open room page (and the waiting popup) renews it with a heartbeat every 10 seconds (`POST /api/study-groups/sessions/{id}/heartbeat`), and an explicit Leave Session, closing the waiting popup or leaving the Study Group releases it. A seat nobody renews for 30 seconds is released, dated to the moment its lease ran out. Nothing else opens or closes a seat: the page-unload beacon is a no-op, and LiveKit webhooks are verified and recorded but never change a seat or a session. The earlier mix of unload beacons, provider webhooks and a provider participant sweep disagreed with each other, which left rooms live and seats held after the last person closed the tab or lost the network (QA 2026-10-19).

A live session ends when an explicit Leave releases its last seat (PRD BR-026 / BR-027), or when it has had no seat for 60 seconds, dated to the moment it became empty. The grace is what lets a refresh come back to the same live session (BUG-0108). The sweep runs on the runtime timer, on the reconciliation tick, and at most once per 30 seconds on the request path, so a store whose timers are not running still ends abandoned sessions.

## AI Tutor limits

Each participant may have two questions waiting for the AI Tutor at once (`tutor_busy`, 409) and may ask five per minute (`tutor_rate_limited`, 429). The queue route returns as soon as the question is stored; the answer arrives in the room. Each answer carries `replyTo` — the asker's name and the first 80 characters of the question — so everyone can see what it answers. A question whose session is no longer live is settled as `session_ended` without calling the model.

## Related Lesson

The schedule control lists the titles of that course's lessons. The choice is optional. A blank choice stores no lesson id. Discover cards do not show it. The group sheet can show the stored lesson title.

## Duration

The Host chooses 30, 45, 60, or 90 minutes. Those choices are stored as 1800, 2700, 3600, and 5400 seconds. No other duration is accepted. The session title is at most 20 characters.

## Schedule dialog

The Schedule Live Session dialog keeps the browser's native date and time inputs — chosen for cross-browser behaviour and accessibility over the dropdown selectors shown in the latest Figma (owner decision, 2026-10-13).
