# Phase 1：API contract

Helpdesk Tickets v1 (2026-10-28, [helpdesk-tickets.md](helpdesk-tickets.md)). These endpoints do not use the `{ ok }` envelope: success bodies are plain JSON (`Cache-Control: no-store`) and errors are RFC 9457 `application/problem+json` `{ type: "https://www.ilovelearningguide.com/problems/<code>", title, status, detail, code, field?, currentSequence? }`. Every create POST requires `Idempotency-Key: <uuid>` (bare or quoted); an identical retry returns 200 with `Idempotent-Replayed: true`, a changed payload 409 `idempotency_conflict`. Writes on an existing ticket carry `expectedSequence` (ticket.sequence last seen). Learner (session cookie; learner POSTs must be same-origin): `POST /api/helpdesk/tickets` multipart `category` (technical_support|course_content|payments_subscriptions|other — Figma addendum), `subject` (1–120), `body` (1–5000), `locale` (en-GB|zh-CN), optional `contactEmail` (defaults to the account email; required when the account has none), optional `suggestionId` (declined AI suggestion → event `suggestion_declined`), `files[]` (0–5 files ≤10 MB each: PNG/JPEG/WebP/GIF/PDF by magic bytes, DOCX/XLSX by ZIP structure, TXT/CSV by extension + clean UTF-8; never html/svg) → 201 TicketDetail (+`contactEmail`); the two multipart POSTs refuse a body over 51 MB (5 × 10 MB + 1 MB) with 413 `attachment_too_large`; `GET /api/helpdesk/tickets` → `{ tickets: TicketSummary[] }`; `GET /api/helpdesk/tickets/{id}` → TicketDetail (no internal notes); `POST …/{id}/messages` multipart `body`, `expectedSequence`, `files[]` → 201 TicketDetail; `POST …/{id}/actions` JSON `{ action: cancel|confirm|reject|close|rate, expectedSequence, rating? (1–5, rate), message? (reject) }` → 200 TicketDetail; `GET /api/helpdesk/attachments/{id}` → bytes, `private, no-store`, `nosniff`, sandbox CSP; images `inline`, other types `attachment`; owner only. Admin-owned Q&A (logged-in, thin pass-through to Admin with `ADMIN_HELPDESK_BASE_URL` + `ADMIN_HELPDESK_TOKEN`): `GET /api/helpdesk/common-questions?locale=` → `{ questions: [{id,category,question,answer}] }` (60 s cache + ETag, stale on error, `[]` = hide); `POST /api/helpdesk/suggestions` JSON `{category,subject,message,locale}` → `{ suggestion: {id,qaId,question,answer} | null }` (null on any failure or the 4 s timeout; creates no ticket); `POST /api/helpdesk/suggestions/{id}/outcome` `{outcome: solved|declined|edited}` → 204, or 503 `assistant_unavailable`. Integration (`Authorization: Bearer $PORTAL_HELPDESK_TOKEN`, read per request, constant-time; unset → 503 `integration_disabled`, wrong → 401 `invalid_token` + `WWW-Authenticate: Bearer`): `GET /api/integration/helpdesk/tickets?status=<status|needs_reply|all>&q=(number, name, account/contact email, subject)&category=&tag=&limit=(1–100, default 20)&cursor=` → `{ tickets: AgentTicketSummary[] (+contactEmail, preview, unreadByAgent, tags), nextCursor, counts }`; `GET …/tickets/{id}` → AgentTicketDetail (+suggestionId, read-only `student` and `subscription` projections, tags); `POST …/{id}/messages` `{ body, internal, agent:{id,name}, expectedSequence }` → 201 (a public reply emails the contact email); `POST …/{id}/actions` `{ action: claim|propose_resolution, agent, expectedSequence }` or `{ action: add_tag|remove_tag, agent, tag (≤32, ≤10 per ticket, idempotent) }` or `{ action: mark_read, agent, expectedSequence? }` (with expectedSequence the unread flag is cleared only while the ticket is still at that sequence) → 200; `GET /api/integration/helpdesk/attachments/{id}`. Codes: 400 invalid_request, validation_failed (+field), too_many_attachments, idempotency_key_required; 401 unauthenticated, invalid_token; 403 forbidden_origin; 404 not_found (unknown or someone else's ticket/attachment); 409 idempotency_conflict, stale_ticket (+currentSequence), invalid_transition, reopen_window_passed, rating_window_passed, already_rated, tag_limit_reached; 413 attachment_too_large; 415 attachment_type_unsupported; 503 integration_disabled, helpdesk_unavailable, assistant_unavailable. Response shapes are the exported types in `contracts/helpdesk.ts` (TicketSummary, TicketDetail, AgentTicketSummary, AgentTicketDetail, HelpdeskCloudEvent).

Study Group uses `{ ok, code, message, data }`. `GET /api/study-groups?view=discover|mine|courses|reminders` lists public groups, the caller's groups, courses the caller can access, or the caller's reminder notifications. Discover leaves out a group whose related Course is no longer available; every group view carries `courseAvailable`, false (with an empty `courseTitle` and `courseSlug`) for such a group. Such a group cannot be joined: its `canJoin` is false and `join` answers `course_unavailable` (409) to a caller who is not already a member. `POST /api/study-groups` creates a Group for a caller with valid Course access. Group and Session mutations live under `/api/study-groups/:groupId` and `/api/study-groups/sessions/:sessionId` (`join`, `leave`, `cancel`, `plan`, `cancel-attendance`, `enter`, `heartbeat`, `start`, `token`, `ai-tutor`, `tutor`). `POST /api/study-groups/sessions/:sessionId/heartbeat` renews the caller's seat lease. A renewed seat returns `{ seated: true }` (a one-row write); otherwise it returns `{ seated: false, occupancy, state }`, meaning the seat lapsed and the page must enter again. A seat renews only while its session is live, or in Starting Soon before its planned end; a session moved back out of Starting Soon, or a waiting room left open past its planned end, releases the seat at the next heartbeat or entry (`seated: false`, and `enter` answers `session_not_open`). Session duration is `durationSeconds` and must be 1800, 2700, 3600, or 5400. `POST /api/study-groups/sessions/:sessionId/ai-tutor` accepts `{ message }` from the room. `POST /api/study-groups/sessions/:sessionId/tutor` accepts `{ text, clientEventId }`. Both call `enqueueTutor`. The response is the queue item and has no tutor answer. A caller with two questions still waiting gets `tutor_busy` (409), and more than five questions in a minute gets `tutor_rate_limited` (429). A caller whose seat lease ran out gets `seat_lapsed` (409) until the room re-enters; a caller who never entered or left gets `forbidden` (403). The answer, when one is published, goes to the shared LiveKit chat. A question that cannot be answered (the model failed, the answer's publish kept failing, or every attempt at it died with its process) produces one `unavailable` message for it instead of silence. The system prompt stays on the server. The token response is a short-lived LiveKit participant token for that user and Session, with no Host grant and no stored raw token. LiveKit configuration, project state or provider failure returns a typed `unavailable` (503) that keeps the caller's admission row and writes no audit record, except that a rate-limited or unreachable provider returns `livekit_temporarily_unavailable` (503, "try again") with the same guarantees; no response includes a credential, secret reference, or internal project id. Title is at most 50 characters, the session title is at most 50, and About is at most 200. Maximum participants is 2–6, including the Host. A full live session refuses another entry, including the Host, except a caller the provider-verified LiveKit room still has connected (their seat lease lapsed mid-call): the seat moves back to them from the newest holder who is not in the room; during Starting Soon the last seat is kept for the Host. Starting the session gives the Host a seat in the same write, so nobody can take it before the Host's own entry. A session view carries `seatsOpen`: the seats a member who is not the Host can still take (during Starting Soon the Host's kept seat is subtracted until the Host holds one; 0 before Starting Soon, for a waiting room past its planned end, and once the session has ended). It also carries `viewerSeated`: true while the caller holds a seat in it (a reload or a second tab), so a session with `seatsOpen` 0 is still open to that caller, whose entry renews the same seat. A live session whose seats have all lapsed for 60 seconds ends, unless the provider-verified LiveKit room still has a member of the session's Study Group connected (heartbeats failing while the call goes on); anyone else still connected to such a room is removed from it.

`view=reminders` requires a signed-in caller and returns up to five `{ body, createdAt }` Live Session reminder or Study Group cancelled notifications for that caller; other notification types are not returned. ## Understanding participation

GET /api/courses/:courseId/understanding requires Session, published Course and current Entitlement. Returns {ok,data:{completed,total,percent,lessons:[{id,number,title,state,knowledge,application}]},requestId}. Each assessment summary has status (not_started/in_progress/completed/submitted), answered,total,percent,score (Knowledge self-assessment only; Application always null). Course numbers/titles/counts come from current server Course metadata. Empty collections yield zero progress.

GET/PUT /api/courses/:courseId/lessons/:lessonId/assessments/:kind require the owning authenticated user, current Course access, validated Lesson ownership and Study completion for new attempts. GET returns the current saved record or null. PUT accepts {clientEventId:UUIDv4,expectedVersion:nonnegative integer,attempt}. Knowledge attempt is {kind:"knowledge",responses:[{answer,rating:null|"right"|"wrong"}],index,phase:"question"|"answer"|"result"}; the response count must match server sample cards and result requires every self-rating. Application attempt is {kind:"application",answer,phase:"answer"|"submitted"}; submission requires a trimmed nonblank answer. Answers are bounded to 2000 chars. Client-supplied user IDs, percentages, AI results and timestamps are never trusted. Successful writes increment version once; identical retries with the latest event key return the same record. Changed/stale revisions return 409 ASSESSMENT_CONFLICT without overwriting another tab. 400 invalid payload, 401 unauthenticated, 403 expired/unowned/uncompleted access, 404 unknown/unpublished Course or foreign Lesson/kind, 503 storage unavailable. All responses use private,no-store and Vary:Cookie. Application submission records participation only; this slice adds no real question-generation or AI grading API.

Text Next lesson completion (2026-10-22): no new endpoint or database field. The existing POST /api/study/events (or entitled /api/study/preview) complete event with learningMode:text and completeLesson:true is saved before the client opens LessonCompletedDialog and shows current-Lesson 100%. Server-derived completedContentIds restore text/PDF completion after reload; the existing legacy whole-Lesson flag restores body-only completion. Dialog Continue navigates to the server-provided next Lesson or localised My Learning without another completion write. The Course record.progress remains its server-calculated maximum outline percentage. Failed saves have no success/navigation and retry with the same clientEventId.
