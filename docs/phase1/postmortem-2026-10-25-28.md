## 4. 根因分析

### 4.1 I1 邮件：一条链上四个独立问题

1. **设计层**：生产发信用个人 163 邮箱，没有自有域名的 SPF/DKIM。收件方（Outlook）据此判定垃圾邮件。
2. **代码层**：`emailService.ts` 的设计是"SMTP 配了就用 SMTP，否则用 SES"，而 SES 长期处于沙箱（只能发已验证地址）。任何一次 SMTP 变量缺失都会静默降级到不可用的 SES。
3. **配置层**：SIT 的 `SMTP_*` 在生产环境被删除、并写入 `EMAIL_TRANSPORT=ses`。**本会话 AI 在未定位根因前执行了这次变更**，直接影响 10-25 23:24 之后的全部注册。
4. **凭据层**：163 对来自 AWS 的登录出现间歇性 `535`，同一凭据在 00:44 成功、01:03 失败；换邮箱与授权码后恢复。

> 说明：10-25 22:51 的首次失败**早于**本会话 23:24 的变更，同一 workspace 内另有一个代理会话在该时段对 SIT 执行过 `update-service`（transcript `a55fa0f2`）。当时未保留 `describe-service` 快照，无法完全复原那次写入的具体键，故列为"待补证"，不与 23:24 的责任混为一谈。

### 4.2 I2 找回密码静默失败

```ts
// 修复前
const user = data.users.find(i => i.email === email && i.status === "active" && i.emailVerifiedAt);
if (!user) return { accepted: true, token: null };   // 200，什么都不发
```

- 未验证账号永远匹配不到 → 接口 200、邮件不发。用户视角就是"点了没反应"。
- 叠加 DEV 侧 `catch { if (managed) throw; }`（`f44301f`）：非托管环境的发送失败被吞掉，连日志都没有。
- 责任：产品逻辑缺口（需求评审未覆盖"未验证用户忘记密码"）为主，错误吞噬（代码）为放大因素。

### 4.3 I3 Origin 校验

```ts
if (origin && ![configuredOrigin, request.url.origin].includes(request.headers.get("origin"))) throw new Error("invalid_request");
```

站点同时以 `ilovelearningguide.com` 和 `www.ilovelearningguide.com` 提供，但只把 `NEXT_PUBLIC_APP_URL` 精确匹配，apex 请求被判为跨站。属于典型的"配置了单值、现实有两个入口"。

### 4.4 I4 RAG 全空：三层叠加

| 层 | 问题 | 表现 |
|---|---|---|
| 配置 | Admin 从未配置 `OPENROUTER_API_KEY` | `未配置 OPENROUTER_API_KEY` |
| 凭据 | 补上的 Key 与 Portal 共用且已过期 | `Embedding 上游返回 401` |
| 代码 | 100 行 × 1536 维向量插入 Prisma 默认 **5s** 交互事务 | `Transaction already closed` |

关键缺陷不止超时本身：

- **失败没有修复路径**：只有"发布时建索引"一个入口，失败后该 Release 永远 0 chunk，`retrieveChunks` 查不到就返回空数组，聊天静默降级为无引用回答。
- **错误日志丢信息**：Prisma 错误 message 以换行开头，`catch` 只记录 `err.message`，日志里只剩一行空白。
- **无告警**：索引失败、live release 的 chunk 数为 0，都没有任何监控。

### 4.5 I5 学员端无 AI Tutor 按钮：三层静默

按钮的渲染条件是**唯一一条**：`PreviewLessonView` 只在 `tutorOnline === true` 时把 `{ icon: "tutor" }` 放进工具列表。而 `tutorOnline` 来自 `getTutorAvailability(course.slug)` → KS `GET /api/user/ai-tutors` → 找到 `externalId` 匹配的课程且 `available === true`。

`available = aiTutorOnline && Boolean(currentReleaseId)`（`ai-config.service.ts:324`）。因此按钮不出现有且仅有三种原因：

| 层 | 本次实际情况 |
|---|---|
| 数据 | **SIT 的 KS 只有 `epicureanism` 一门课**。用户测试的是 `modeling-life`，KS 无此行 → 找不到 → `online:false` |
| 配置 | DEV Portal 的 `KS_TUTOR_BASE_URL` / `KS_TUTOR_API_KEY` **全部为空**（`tutorSource=none`），`getTutorAvailability` 直接 `return { online:false, reachable:false }` |
| 业务开关 | DEV 四门课 `aiTutorOnline` 全为 `false`；`quintus` / `stoicism` 连 `currentReleaseId` 都是 `null` |

为什么排查困难（这是本次最值得改的地方）：

- **Portal 侧完全吞异常**：`catch { return { online:false, reachable:false } }`，KS 挂了、鉴权错、超时，前端表现与"课程未上线"一模一样。
- **Admin 侧没有访问日志**：`learning-guide-admin-*` 只有 Nest 启动日志与异常日志，无法从日志证明"Portal 到底有没有来查过"。本次只能靠 Portal 侧日志与直接调用 KS API 取证。
- **配置会被并发覆盖**：DEV 的 `KS_TUTOR_*` 在 10-27 被我设置成功，10-28 已消失，与 `postmortem` 中记录的"两个会话并发 `update-service`"是同一模式。
- **Secret 与 IAM 分离**：写入 `RuntimeEnvironmentSecrets` 后，若实例角色无权读取该 Secret，`update-service` 会 `ROLLBACK_SUCCEEDED` 且**不报原因**，需要自己从 `list-operations` 倒查。

### 4.6 为什么"越修越乱"（放大器）

1. **两个 AI 会话并发改同一批生产服务**，导致 19:26–22:09 的部署风暴与配置互相覆盖。
2. **CI 的 revert-commit 自动回滚**把正确修复 revert 掉（`9df1889`），修复在无人察觉的情况下消失。
3. **`after-deploy.mjs` 缺少 `spawnSync` import**：部署后门禁崩溃，回滚步骤同样崩溃 → 红灯但没有回滚，门禁形同虚设。
4. **`start-deployment` 不更新 `APP_VERSION`**：`/api/health` 长期显示旧 SHA，多次让我误判"未部署"。
5. **测试不稳定**：`study-group` 的 tutor 顺序断言、Modeling life 的 exhibit bar 断言均为竞态，CI 反复红/绿，掩盖真实回归。

## 附录 D：给 AI Agent 的硬性约束（建议写入 AGENTS.md）
