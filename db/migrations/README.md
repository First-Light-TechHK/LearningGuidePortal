# Database migrations

Migration 按数字顺序执行。每次变更都要有唯一约束、回滚说明和 integration test。当前计划顺序见 `docs/phase1/domain-model.md`：User/Account → Course → Plan/Price → Order/Payment → Subscription/Entitlement → Study → Notification/Audit → KS links。

本地可以使用 Docker PostgreSQL；DEV、SIT、UAT、PPE/PROD 使用各自的 RDS 数据，不共享生产数据。不要在 Route Handler 中直接写 SQL。

`014_contact_requests.sql` adds the Contact support queue. `npm run contact:migrate` is a non-connecting dry run; `npm run contact:migrate -- --apply` performs the idempotent schema bootstrap against the configured database. The bootstrap/probe mirrors this artifact. No product/account/payment data is backfilled or rewritten. Roll back the application while retaining this table; deleting support history requires a separate export/retention decision.

`017_helpdesk_tickets.sql` adds Helpdesk Tickets v1 (tickets, per-day number counter, messages, attachments, CloudEvents-named events, and — folded in from the 2026-10-28 Figma addendum before 017 reached any shared branch — the four enquiry-type categories, `contact_email`, `suggestion_id`, `unread_by_agent`, up to 5 attachments of 10 MB in nine types, and `helpdesk_ticket_tags`). It is additive and repeatable; `services/persistence/db.ts` mirrors it in the startup bootstrap and freshness probe (parity pinned by `tests/unit/helpdesk-migration.test.ts`), so the normal startup path applies it. `npm run helpdesk:migrate` is a non-connecting dry run; `npm run helpdesk:migrate -- --apply` runs the bootstrap against the configured database. No existing data is touched. Roll back the application and retain the tables; dropping support history needs an export/retention decision. PostgreSQL proof: `tests/io/postgres/helpdesk-repository.test.ts`.

`018_helpdesk_v2.sql` adds Helpdesk v2 (tickets-v2-figma-addendum §4a): `helpdesk_tickets.flagged_at` / `flagged_by` (+ partial index) and `helpdesk_assist_log` (every AI answer the learner was shown, with feedback and the ticket it was linked to). Additive and repeatable; mirrored in the `services/persistence/db.ts` bootstrap and freshness probe and pinned by `tests/unit/helpdesk-migration.test.ts`; PostgreSQL proof in `tests/io/postgres/helpdesk-repository.test.ts`. 017 is not edited. Rollback: roll back the application and retain the columns and the table. The old Admin `helpdesk_questions` tables are Admin's to clean up later; Portal never had them.

`019_helpdesk_outcome_delivery.sql` adds `helpdesk_assist_log.feedback_delivered_at` / `feedback_attempted_at` (+ a partial index on undelivered rows) so an assist outcome Admin missed during an outage is re-sent by the server (on a repeat, after a ticket records "declined", and by a small sweep while Admin answers). Additive and repeatable, mirrored in the bootstrap and probe like 018; 017 and 018 are not edited. Rollback: roll back the application and retain the columns.

`020_helpdesk_ai_ratings.sql` adds Helpdesk v3 (helpdesk-v3-alternatives-rating): `helpdesk_ai_ratings` (one 1–5 rating per answer the learner was shown, keyed by the `helpdesk_assist_log` row, first wins) and the nullable `helpdesk_assist_log.alternatives` (the "You might be asking" questions shown with a missing answer, so a replay is the same). Additive and repeatable; mirrored in the `services/persistence/db.ts` bootstrap and freshness probe (so the normal startup path applies it on deploy) and pinned by `tests/unit/helpdesk-migration.test.ts`; PostgreSQL proof in `tests/io/postgres/helpdesk-repository.test.ts`. 017–019 are not edited. Rollback: roll back the application and retain the table and the column.

`022_helpdesk_order_link.sql` adds Helpdesk v4 Part A (helpdesk-v4-order-and-chat-end): the nullable `helpdesk_tickets.order_id` (1–64 characters), the learner's own order an enquiry is about, checked by Portal code before it is stored. No foreign key (the order record stays the payment module's) and nothing is backfilled; existing tickets read as "no order". Additive and repeatable; mirrored in the `services/persistence/db.ts` bootstrap and freshness probe (so the normal startup path applies it on deploy) and pinned by `tests/unit/helpdesk-migration.test.ts`; PostgreSQL proof in `tests/io/postgres/helpdesk-repository.test.ts`. 017–020 are not edited. Rollback: roll back the application and retain the column.

`023_helpdesk_chat_sessions.sql` adds Helpdesk v5 (helpdesk-v5-faq-graph-design §3, helpdesk-v5-context-chips-and-smalltalk Part G1): `helpdesk_chat_sessions` (one row per AI chat session: locale, release version, start / last turn / end with its reason, turn count, unsolved streak, the card on screen and the learner's situation signals as enum names) and nullable `helpdesk_assist_log` columns for each turn's place and path (`session_id`, `turn_index` with a unique (session, turn) index, `node_id`, `parent_node_id`, `via`, `kind`, `intent`, `guard`, `release_version`, `trace_id`, `signals`, `blocks`, `expanded`, `covered`, and `texts`, the short strings shown so a replay is the same). Enum columns are CHECKed against the contract's values. Nothing is backfilled: earlier rows read as "no session". Additive and repeatable; mirrored in the `services/persistence/db.ts` bootstrap and freshness probe (so the normal startup path applies it on deploy) and pinned by `tests/unit/helpdesk-migration.test.ts`; PostgreSQL proof in `tests/io/postgres/helpdesk-repository.test.ts`. 017–022 are not edited (021 is Study Groups'). Rollback: roll back the application and retain the table and the columns.

`024_helpdesk_flywheel.sql` adds Helpdesk v5 Part G (helpdesk-v5-context-chips-and-smalltalk G1/G2, helpdesk-v5-faq-graph-design §3/§5.5): the nullable `helpdesk_assist_log.scrubbed_at` (set once the 180-day retention job replaced the raw text with the scrubbed text), paging and retention indexes on `helpdesk_assist_log (created_at, id)`, a `helpdesk_tickets (user_id, created_at, id)` index and a partial index for the newest public agent reply; `helpdesk_job_runs` (one row per run of a Portal background job: job, UTC day, trigger schedule|manual, status running|succeeded|failed, attempts, cutoff, rows scrubbed, more due, instance, who asked for a manual run and its Idempotency-Key; a partial unique index allows one scheduled run per job and day); and the view `helpdesk_assist_outcomes`, which links each assist turn to its enquiry (the linked ticket, otherwise the learner's next ticket within 24 hours), its status and close reason, whether the agent resolved it, and the agent's last public reply. The view computes the outcome from the tickets, so nothing is copied. Additive and repeatable (`IF NOT EXISTS`, `CREATE OR REPLACE VIEW`); mirrored in the `services/persistence/db.ts` bootstrap and freshness probe; pinned by `tests/unit/helpdesk-migration.test.ts`; PostgreSQL proof in `tests/io/postgres/helpdesk-insights.test.ts`. 017–023 are not edited. Rollback: roll back the application and retain the table, the view and the column (an older Portal ignores them; `DROP VIEW helpdesk_assist_outcomes` is safe at any time).
